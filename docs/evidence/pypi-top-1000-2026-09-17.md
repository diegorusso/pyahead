# PyPI top-1000 validation, 17 September 2026

The second run of the protocol in `docs/pypi-validation.md`, against the
registry after the analysis window opened at Python 3.8 and the Python 3.9 and
3.10 "What's New" sections were curated. It exists because the 11 September
record measured precision with the window at 3.11, and the fifty-six rules
added since had never been run against real code.

## Decision

- Prepared by an agent on 17 September 2026; **not yet approved**. Under the
  repository's gate convention an agent may prepare and verify this evidence
  but cannot approve it.
- Recommended decision: release. Two of the new rules were refuted on every
  adjudicable finding and have been retired before this record was written;
  the remaining refutations are the same seven open rows the September record
  already carries, unchanged.

## What changed since September, and what it did

The window at 3.8 changes which interpreter a package is scanned under. The
runner picks the lowest installed minor its `requires-python` admits, so a
package declaring `>=3.8` is now scanned at 3.8 rather than 3.11, and rules
whose events fall between become reachable for it. 391 packages in this corpus
declare a floor below 3.11.

Two harness changes were needed to make that true, both landed on `main`
during the run:

- The harness hardcoded a baseline of 3.11 for choosing the reference
  interpreter. It now reads the window's floor from the registry. Without
  this, every package would have been scanned at 3.11 and none of the new
  rules would ever have fired.
- **Reference floors.** The wheelhouse holds one artifact per package, the
  current release, acquired under 3.11. At a 3.8–3.10 reference, 467 packages
  could not install their dependency tree: a dependency's current release
  requires a newer Python (`anyio`, `markdown-it-py`, `referencing`), or ships
  only a `cp311` wheel (`charset-normalizer`), or a compiled dependency has no
  artifact for that tag (`pydantic-core`). The first pass scanned 494 packages.
  The runner now tries each admitted minor in ascending order and settles on
  the lowest the package installs under, recording every rejected candidate
  and its reason in the shard. The second pass scanned 796 — one fewer than
  September. **297 packages settled above their declared floor**, and their
  baseline is the lowest floor they genuinely work at with current
  dependencies, not the one they declare.

  Reference minors after fallback: 3.8: 174, 3.9: 88, 3.10: 192, 3.11: 328,
  3.12: 13, 3.15: 1.

A package's declared `requires-python` being stale relative to its dependency
tree is a real property of the ecosystem, and worth knowing, but it is not
what this record measures.

## Precision

Agreement rose from September's figure to 98.49%, and `binding-not-visible`
fell from 835 to 130 — the earlier investigation's fixes carried through.

All eighteen refutations are module imports, and all eighteen are the same
phenomenon: an `import` inside a branch that never executes on the Python it
was scanned under. PyAhead reports the statement; the oracle judges the
program.

### Retired: `dummy_threading` and `_dummy_thread`

Eleven adjudicable findings, eleven refuted: `pip`, `distlib` (three sites),
`joblib`, `future` (three sites), `celery`, `cffi`, `sortedcontainers`. Every
one is `try: import threading` / `except ImportError: import dummy_threading`,
or the `_thread` equivalent. The probe found the fallback module absent and the
bound name owned by the primary import, as it always will be: `threading` and
`_thread` exist in every Python 3, so the fallback branch is unreachable by
construction.

These two modules existed *only* to be that fallback, so there is no other
shape their use could take. A rule that is right about the timeline and wrong
about every real program it meets is a false positive with a source citation.
Both rules are retired, their IDs reserved, and the census entry for the page
records the reason and the packages it was seen in, so the same rule is not
written again in good faith.

### The seven open rows

Identical, file and line, to the September record's open rows, less `ddtrace`,
whose site is not in its current release:

- `future` — `libpasteurize/main.py:44` (CPY0027), `future/backports/test/support.py:36`
  (CPY0023), `future/backports/urllib/request.py:1590` (CPY0108)
- `gevent` — `gevent/_compat.py:103` (CPY0024)
- `hypothesis` — `hypothesis/strategies/_internal/regex.py:29` and `:30` (CPY0117)
- `passlib` — `passlib/utils/__init__.py:854` (CPY0008)

Their reasons stand as written there: `except ImportError` fallbacks that never
run on 3.x, one platform-conditional import, two oracle limitations. Four of
the seven, and all eleven of the retired rules' rows, share the fallback shape.
The September record called extending the reachability grammar to it a
roadmap decision; this run makes the case for it stronger — fifteen of
eighteen refutations — and no more settled.

## Not adjudicable

`import-error` (71) and `module-not-importable` (49) are largely the
CPython-tagged wheels: a `cp311` artifact cannot be installed under the 3.10
that a 3.11-removal probe needs, so its pre-3.11 findings cannot be judged.
This is the one-artifact acquisition again; a multi-interpreter wheelhouse
would close it and is out of this record's scope.

## Skipped

in the report; the timeouts are large generated packages and match
September's.
