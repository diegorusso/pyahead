# PyAhead 0.1.0a2 release readiness: M8.5 audit, Windows rooted-input blocker, and maintainer handover evidence

## Overview

Take over maintenance of `diegorusso/pyahead` at `origin/main` (`de9805e2ef983009175bb62b689372e8ffdc00fd`) and bring the existing `0.1.0a2` public-alpha candidate to the point where the maintainer can perform final release approval.

Investigation of the current main branch has already established the following facts, which this plan acts on rather than re-discovers:

1. One demonstrated release blocker exists. Since M8.5a introduced `src/pyahead/_rooted_reader.py` and the native Windows path in `src/pyahead/_windows_output.py`, **all root-bounded reads on Windows report a missing file as a generic `OSError` instead of `FileNotFoundError`**. `_NtStatusError` (`src/pyahead/_windows_output.py:147`) formats the raw NTSTATUS and never translates it, so every caller that distinguishes "absent" from "unreadable" — `config.py:126`, `baseline.py:126`, `evidence.py:783`, `analysis/discovery.py:274/494/505`, `registry/loader.py:334/372`, `dependencies.py:1223/1488` — takes the wrong branch. The visible symptom is `pyahead: error: pyproject.toml: unable to read configuration` for any project without a `pyproject.toml`, with exit 2 instead of 0/1/3. CI run `33451407963` on `2f21349` failed with **394 test failures** on `windows-latest` Python 3.11 and 3.14 (`NtCreateFile failed with NTSTATUS 0xc0000034` = `STATUS_OBJECT_NAME_NOT_FOUND`); the last green Windows run was `32993595876` on `ea25f72` (M8), confirming M8.5 as the regression window.

2. A genuine release-version conflict exists and is a **product-decision blocker, not an implementation task**. `docs/design.md:2125` titles the implemented milestone "M8.5 — 0.2 release hardening", and `docs/design.md:211` (§4.3) assigns dependency metadata/resolver evidence and pytest warning collection — that is, the delivered M7 and M8 — to release `0.2`, while `docs/design.md:196` (§4.2) scopes `0.1.0a2` to the static analyser only. The package and README nevertheless identify the candidate as `0.1.0a2`. This plan reports the conflict and **does not choose a version**.

3. CI on the exact candidate commit has completed and **failed**. Run `33452911860` has `headSha == de9805e2ef983009175bb62b689372e8ffdc00fd`, conclusion `failure`, with exactly two failing jobs: `Tests / windows-latest / Python 3.11` and `Tests / windows-latest / Python 3.14`. Every other job — the Linux and macOS matrix, `Build wheel and sdist`, and all `Install wheel and sdist` jobs — succeeded. This confirms the Task 2 blocker against the candidate commit itself and isolates it to the Windows rooted-read path.

The plan contains exactly one behavioural change (the NTSTATUS translation), its tests, its changelog entry, a complete local verification and evidence pass, and — per the draft review — pushing `main` and driving GitHub Actions to a fully green run on the new candidate commit. It adds no features, no provider, no M9/M10 work, and no speculative refactoring.
